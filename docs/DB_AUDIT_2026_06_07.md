# Database Audit — 2026-06-07

This audit was performed as part of the 5-day release-prep sprint.
The live Neon DB was not reachable from the sandbox (the Neon HTTP driver
returned `403 Host not in allowlist` and direct port 5432 was firewalled
out), so the findings below come from a static comparison of
`prisma/schema.prisma` against query patterns in `app/`, `lib/`, and
`worker/`. Apply the recommendations after running `EXPLAIN ANALYZE`
against the live data to confirm cardinalities — the suggestions are
conservative but a one-shot read against production tells you which
ones actually pay for themselves.

## How to apply the new indexes safely on Neon

1. Schedule the work for an off-peak window. Even with `CONCURRENTLY`,
   index builds on the larger tables (`AnswerEvent`,
   `StudentConceptState`) can take minutes.
2. For each index in `prisma/migrations/20260607000000_add_audit_indexes/migration.sql`,
   run the equivalent **`CREATE INDEX CONCURRENTLY IF NOT EXISTS`** manually
   first (Prisma migrations don't support `CONCURRENTLY`):
   ```sql
   CREATE INDEX CONCURRENTLY IF NOT EXISTS
     "AnswerEvent_studentId_sessionId_idx"
     ON "AnswerEvent"("studentId", "sessionId");
   ```
3. Then mark the Prisma migration as applied without running its body:
   ```bash
   npx prisma migrate resolve --applied 20260607000000_add_audit_indexes
   ```
4. Verify with `\d+ "AnswerEvent"` and `pg_stat_user_indexes`.

## Indexes added in this commit

| # | Table | Columns | Reason |
|--:|-------|---------|--------|
| 1 | `ParentStudent` | `(parentId, status)` | Parent dashboard reads all active links per parent on every visit. |
| 2 | `StudentConceptState` | `(studentId, updatedAt)` | Parent progress + recent-mastery delta compute uses a `updatedAt >= 7 days ago` filter scoped to a single student. |

## Findings deliberately NOT acted on

- **`WeeklyStudentSummary (studentId, weekStart)`** — the existing `@@unique([studentId, weekStart])` already builds a btree the planner can use for the `weekStart >= ...` range scan. Adding a second composite would only duplicate it.
- **`Question(status, topicId, difficulty)` reorder** — the existing `(topicId, difficulty, status)` and `(board, grade, subject, status)` indexes already cover the hot lookups. A reorder is a separate, risky migration (`DROP INDEX` is non-additive) and should not be touched before more telemetry.
- **Denormalising `chapterId` onto `Concept`** — the JOIN through `Topic` in `irtWorker.ts:149` is ~1 hop and runs once per session completion, not per dashboard load.

## Operational checks to run on the live DB (read-only)

Paste these into psql once allowlisted to confirm the audit's assumptions
before paying the index-build cost:

```sql
-- 1. Identify the largest tables (where indexes pay back the most)
SELECT relname, pg_size_pretty(pg_total_relation_size(c.oid)) AS total,
       pg_size_pretty(pg_relation_size(c.oid)) AS data,
       pg_size_pretty(pg_indexes_size(c.oid)) AS idx
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r'
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 25;

-- 2. Identify unused indexes (candidates for DROP -- separate migration)
SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE schemaname = 'public' AND idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 25;

-- 3. Top queries by total time (requires pg_stat_statements)
SELECT substring(query, 1, 80) AS q,
       calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       rows
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_%'
ORDER BY total_exec_time DESC
LIMIT 25;

-- 4. Seq scans on hot tables (before vs after the new indexes)
SELECT relname, seq_scan, seq_tup_read, idx_scan, idx_tup_fetch
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname IN (
    'AnswerEvent', 'StudentConceptState', 'ParentStudent',
    'DiagnosticSession', 'StudentTopicProgress', 'WeeklyStudentSummary'
  )
ORDER BY seq_tup_read DESC;
```

## Things the static audit cannot tell you (still TODO)

- **pg_stat_statements top queries** — the audit assumes the
  dashboard/parent-progress paths are the hottest, but only
  `pg_stat_statements` (or the Neon console) can confirm which queries
  are actually consuming wall-clock and IOPS.
- **Bloat / vacuum status** — frequently-updated tables like
  `StudentConceptState` and `StudentTopicProgress` may have accumulated
  dead tuples. Run `VACUUM (ANALYZE, VERBOSE)` and check
  `pg_stat_user_tables.n_dead_tup`.
- **Index bloat** — `pgstattuple` extension can quantify dead bytes per
  index; rebuild candidates surface there.
- **Connection saturation** — Neon's default pool is small. The parent
  progress refactor in this branch dropped peak connection holding from
  N-children × M-subjects serial waits to one parallel burst; confirm
  the new burst doesn't push past `max_connections` under load.
