# Database Audit — 2026-06-07

This audit was performed as part of the 5-day release-prep sprint.
The schema-level findings below were later validated against live Neon
telemetry (`pg_stat_user_indexes`, `pg_stat_statements`,
`pg_stat_user_tables`). The live data both confirmed some of the
predictions and revealed a hot polling loop that wasn't visible from the
static audit.

## Live telemetry highlights (the data, not speculation)

- **DB is small.** Largest table (`AIContentLog`) is 10 MB. Hot
  application tables (`User`, `StudentConceptState`, `AnswerEvent`) are
  all well under 200 KB. The proposed composite indexes are still
  correct at scale but are not currently a bottleneck.
- **Real hot path: `check-ready` polling.** `pg_stat_statements` shows
  1,697,521 `COUNT(Question)` calls and 141,166 `COUNT(TopicDef)` calls
  driven by the 5 s client poll on the diagnostic waiting screen.
  Average is 0.03 ms per call so total DB time is modest (52 s
  cumulative) but the call rate is the dominant noise source in the
  query log.
- **`StudentConceptState` seq-scan rate is real.** 1647 sequential scans
  read 176,263 tuples on a table with ~50 KB of data, validating the
  `(studentId, updatedAt)` index added in the parallel migration.
- **Two duplicate `User` indexes.** `idx_user_email` and
  `idx_user_parent_email` have zero scans and duplicate the auto-built
  indexes on the unique constraints. These were added manually and are
  not tracked in the Prisma schema.

## Actions taken in this commit

| Action | Why |
|--------|-----|
| Added Redis cache (8 s positive / 4 s negative TTL) on `/api/student/diagnostic/check-ready` | Cuts the 1.7 M `COUNT(Question)` calls dramatically -- the result depends only on `subjectId`, so the cache is global and one fill serves every concurrent client. |
| Added `prisma/migrations/20260607000001_drop_unused_indexes` dropping `idx_user_email` and `idx_user_parent_email` | Zero scans; duplicate of auto-built unique-constraint indexes. Removing them lowers write amplification on the hot User upsert path (signup, JWT cache writeback). |
| Kept the speculative `prisma/migrations/20260607000000_add_audit_indexes` | The `StudentConceptState` seq-scan rate alone justifies the `(studentId, updatedAt)` index. The others are pre-emptive but cheap to add at this table size and will earn back at scale. |

## How to apply the new indexes safely on Neon

1. Schedule the work for an off-peak window. Even with `CONCURRENTLY`,
   index builds on the larger tables (`AnswerEvent`,
   `StudentConceptState`) can take minutes once they grow.
2. For each index in `prisma/migrations/20260607000000_add_audit_indexes/migration.sql`,
   run the equivalent **`CREATE INDEX CONCURRENTLY IF NOT EXISTS`** manually
   first (Prisma migrations don't support `CONCURRENTLY`):
   ```sql
   CREATE INDEX CONCURRENTLY IF NOT EXISTS
     "AnswerEvent_studentId_sessionId_idx"
     ON "AnswerEvent"("studentId", "sessionId");
   ```
3. Then mark the Prisma migration as applied without running its body:
   ```bash
   npx prisma migrate resolve --applied 20260607000000_add_audit_indexes
   ```
4. The drop migration (`20260607000001_drop_unused_indexes`) is safe to
   run via the normal Prisma flow -- DROP INDEX takes a brief share
   lock, not an ACCESS EXCLUSIVE lock.
5. Verify with `\d+ "AnswerEvent"` and `pg_stat_user_indexes`.

## Findings deliberately NOT acted on

- **Other zero-scan indexes** flagged by `pg_stat_user_indexes`
  (`AIContentLog_promptType_idx`, `AIGenerationLog_*`,
  `SlowQueryLog_*`, `Outbox_queue_sentAt_createdAt_idx`,
  `ContentGap_subjectId_boardSlug_grade_idx`, etc) are kept for now.
  These tables haven't ramped traffic yet, and the indexes may earn
  back once the corresponding read paths warm up. Re-run the
  `pg_stat_user_indexes` query after a full day of production traffic
  and drop the persistent zero-scan entries.
- **`WeeklyStudentSummary (studentId, weekStart)`** -- the existing
  `@@unique([studentId, weekStart])` already builds a btree the planner
  can use for the `weekStart >= ...` range scan.
- **`Question(status, topicId, difficulty)` reorder** -- the existing
  composite indexes already cover the hot lookups. A reorder is a
  separate, risky migration and should not be touched before more
  telemetry.

## Operational checks to run on the live DB (read-only)

Run these from the Neon SQL Editor periodically to keep this audit
honest:

```sql
-- 1. Identify the largest tables
SELECT relname, pg_size_pretty(pg_total_relation_size(c.oid)) AS total
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r'
ORDER BY pg_total_relation_size(c.oid) DESC LIMIT 25;

-- 2. Identify unused indexes (candidates for DROP -- separate migration)
SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE schemaname = 'public' AND idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC LIMIT 25;

-- 3. Top queries by total time (requires pg_stat_statements)
SELECT substring(query, 1, 80) AS q, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms, rows
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_%'
ORDER BY total_exec_time DESC LIMIT 25;

-- 4. Seq scans on hot tables
SELECT relname, seq_scan, seq_tup_read, idx_scan, idx_tup_fetch
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname IN (
    'AnswerEvent', 'StudentConceptState', 'ParentStudent',
    'DiagnosticSession', 'StudentTopicProgress', 'WeeklyStudentSummary'
  )
ORDER BY seq_tup_read DESC;
```

## Things still TODO

- **Re-run the four queries after 24-48 h of production traffic** and
  compare against the current snapshot in this doc. Specifically:
  the `StudentConceptState` seq-scan count should drop dramatically
  once index #2 is in place; the `COUNT(Question)` total time should
  fall to a fraction once the Redis cache absorbs the poll volume.
- **Bloat / vacuum status** -- frequently-updated tables like
  `StudentConceptState` and `StudentTopicProgress` will accumulate dead
  tuples as traffic grows. Run `VACUUM (ANALYZE, VERBOSE)` and check
  `pg_stat_user_tables.n_dead_tup` weekly.
- **Connection saturation** -- Neon's default pool is small. The parent
  progress refactor in this branch dropped peak connection holding from
  N-children x M-subjects serial waits to one parallel burst; confirm
  the new burst doesn't push past `max_connections` under load.

## Findings deliberately NOT acted on

- **`WeeklyStudentSummary (studentId, weekStart)`** — the existing `@@unique([studentId, weekStart])` already builds a btree the planner can use for the `weekStart >= ...` range scan. Adding a second composite would only duplicate it.
- **`Question(status, topicId, difficulty)` reorder** — the existing `(topicId, difficulty, status)` and `(board, grade, subject, status)` indexes already cover the hot lookups. A reorder is a separate, risky migration (`DROP INDEX` is non-additive) and should not be touched before more telemetry.
- **Denormalising `chapterId` onto `Concept`** — the JOIN through `Topic` in `irtWorker.ts:149` is ~1 hop and runs once per session completion, not per dashboard load.
