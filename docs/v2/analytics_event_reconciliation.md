# Analytics Event Reconciliation

Summary: compare server-emitted events (from CSV) against the client `VALID_EVENT_TYPES` allowlist in `app/api/analytics/event/route.ts` and recommend actions.

Client allowlist (`VALID_EVENT_TYPES`):
- lesson_viewed
- lesson_completed
- session_started
- session_completed
- quiz_submitted
- doubt_asked
- streak_updated
- xp_earned
- badge_unlocked

- diagnostic_started

Server-emitted events (canonical list from docs/v2/analytics_event_callsites.csv):
- otp_widget_token (Event table) — [server-only audit]
- trial_start (AnalyticsEvent)
- converted_to_paid (AnalyticsEvent)
- whatsapp_opt_in / whatsapp_opt_out (Event table)
- whatsapp_message_sent (Event table)
- weekly_question_health (AnalyticsEvent)
- ai_call (AnalyticsEvent) — LLM call telemetry (tokens, cost)
- ingest_run / ingest_run_retry (AnalyticsEvent)
- challenge_completed (Event table)
- safety_trigger / safety_triggered / hallucination_detected / hallucination_blocked / copy_paste_detected (AnalyticsEvent)
- Other: client-side allowed types listed above

Findings & Recommendations

- Many server-only operational/ops and AI-guard events (e.g., `ai_call`, `ingest_run`, `weekly_question_health`, safety/hallucination events, WhatsApp opt-ins/sent) SHOULD NOT be accepted from clients. Keep these server-only and refuse client-submitted instances.

- Client allowlist gaps: the client `VALID_EVENT_TYPES` is intentionally narrow. Consider adding the following only if the front-end actually emits them:
  - `challenge_completed` — if the UI can submit it (currently server writes it transactionally). If the client will emit, add to `VALID_EVENT_TYPES` and ensure server-side dedup/idempotency.
  - `subject_selected` — I could not find any explicit `subject_selected` analytics writes. If you want subject selection tracked client-side, add this event to the allowlist and implement a server-side handler to persist it (AnalyticsEvent) and to de-duplicate spurious repeated selections.

- Keep these events server-only (do not add to client allowlist): `ai_call`, `ingest_run`, `ingest_run_retry`, `weekly_question_health`, `safety_trigger`, `safety_triggered`, `hallucination_detected`, `hallucination_blocked`, `copy_paste_detected`, and `whatsapp_*` events. They are internal/ops or contain sensitive metadata and should be generated by server code only.

- Operational vs analytics separation: continue using two tables:
  - `Event` for audit/operational events tied to a user session (opt-ins, challenge_completed, otp_widget_token).
  - `AnalyticsEvent` for analytics/aggregation rollups (funnel events, ai_call telemetry, ingest runs, weekly health). Keep server-only telemetry in `AnalyticsEvent` unless the client is explicitly allowed to emit.

- Action items:
  1. Decide which client events need to be added (e.g., `subject_selected`, `challenge_completed`), then extend `VALID_EVENT_TYPES` and add necessary client instrumentation.
  2. Implement server-side dedup/idempotency for any client-supplied events that can be submitted repeatedly.
  3. Add tests verifying `app/api/analytics/event/route.ts` rejects unknown event types and accepts expected new ones.
  4. Add a lightweight forwarder worker to optionally send sanitized analytics to a 3rd-party sink (PostHog / Amplitude / GA4) from `AnalyticsEvent` for downstream dashboards. See docs/v2/analytics_user_journey.md for recommended aggregator sketch.
